01 / 研究手记

给 idea 办葬礼之前

林李谦2026.09.15约 11 分钟

文中选题 11 条研究线索
ASRO 奖励误差残差分支Strata 调度Zipage 压缩双平面调度HP TCP 传输FreshView 记忆更新HiCache 写回暂缓与未完成的选题留下的判断

最近的科研进展有一种奇怪的形状：idea 越来越少，文件夹越来越多。

算法、学习方法、推理系统，我都试着往前推过。想过修正算法演化的奖励，训练更会补漏的草稿分支，重新安排请求和 GPU，也想过把 KV 压缩、记忆更新、权重传输做得更聪明一点。

它们刚出现时，没有哪个看起来像是来浪费时间的。问题具体，直觉顺畅，方法甚至可以马上开始写。后来有的输给了简单基线，有的输给了成本账，还有的实验跑完了，依然只能写“目前不知道”。

所以这篇记一下：我到底想做什么，又是在哪一步不再相信最初的故事。停止一个方案、暂缓一个问题、没有得到结论，是三件不同的事。

ASRO：想给奖励纠错，先被不等号纠了错

这条是算法方向。ASRO 里，求解算法和出题程序一起演化：一边尝试把题做得更好，一边尝试出更难的题。具体任务是在线装箱——物品陆续到来，要把它们放进容量固定的箱子，尽量少用箱子。

我盯上的是给出题程序打分的参照。如果参照把最优答案估得太好，会不会把“参照不准”算成“题目很难”，再让系统反复选择这些高分题？听起来很适合做奖励修正，而且确实能构造出奖励虚高的反例。

但沿着实际代码看，事情先在一个不等号上拐了弯。求解器超时时，有些返回值来自一个真实可行的装箱方案。它是最优箱数的上界；放进当时的差距奖励公式里，只可能让差距相等或偏低，不会制造我担心的虚高。

“没有证明最优”，不等于“把奖励抬高了”。原本准备修裁判，先得确认裁判究竟往哪边偏。

随后跑的短共同演化里，315 次合法奖励都能排除参照导致的虚高。对唯一可能影响下一轮出题分配的未决样本，追加求解后，原参照恰好就是最优值。按原规则重算，关键候选和实际采样分配没有改变。那个虚高反例，简单计数下界也能修掉。

这次只完整完成了两轮，第三轮因候选被原生多样性规则全部拒绝而中止，不能代表完整训练。停止的是当前“修正虚高奖励，从而改善出题供给”的路线：数学上能写出一个反例，离它在真实演化中改变决策，还有一段距离。

残差分支：专门补漏，未必赢过普通选手

另一条算法线是 MoE 投机解码。我想让额外的 draft branch 专门补上原草稿容易被拒绝的部分，而不是再训练一个差不多的草稿。直觉很自然：A 擅长的交给 A，B 负责查漏补缺。

投机采样中确实存在拒绝后的残差分布。但它是保证采样正确性的数学对象，不会自动变成一种容易学会、可以稳定泛化的“专长”。有空缺，和我能训练一个擅长填空缺的模型，中间还隔着一个实验。

于是我给残差分支配了一个不太客气的对照：同规模、同输入、同初始化和训练预算的普通第二分支。真正要看的是“专门补漏”比“正常再学一遍”多带来了什么。

这一轮在未见题上的加权接受机会增益很小，置信区间跨过零。补做一次较低学习率诊断，两组都改善了，分工本身的优势仍没有被确认。训练集上的信号也没有可靠地带到测试集。

所以它的结论是 INCONCLUSIVE，暂停推进。没有继续扩成小树验证、MoE 成本优化或后面的吞吐实验，更不能说已经加速了。残差存在这件事成立；当前训练方法值得继续投入这件事，还没有成立。

“大家各司其职”是一个很好的组织愿景。模型暂时没有签字。

Strata：总时间赢了，排队的人未必同意

我还追过一个更像算法题的切口：把需要加载 KV 的请求和需要较多计算的请求组合起来，能否用更好的选择顺序，让搬运和计算更充分地重叠？

从 Strata 的论文伪代码出发，我做了选择器重实现和小规模精确对照。在构造的请求队列里，能找到贪心选择留下的空间；这很容易让人接着想写一个新 scheduler。

但抽象模型里的 gap，要落到真实执行上才能算数。第一版 GPU 实验只体现了复制和计算的重叠，复制过去的 KV 还没有被 attention 真正使用。后来补上了真实 KV 消费路径，再看时间和请求完成顺序。

结果没有把总耗时优势全部抹掉：六组预设正例中，三组仍有至少 5% 的整批耗时改善。但同时满足耗时、平均等待代理和暴露停顿改善条件的，只有一组。

这里的等待指标是按 batch 边界计算的代理，不是完整 serving 引擎里的真实逐请求 TTFT。即便在这个有限口径下，一部分更短的排程也让平均等待变差了。

这条线停在预先写好的门槛上。我没有验证官方 Strata 的完整实现，更不能宣布找到了它的生产性能缺陷。对我想做的算法而言，首先需要解释：省下来的时间，到底是谁的时间？

总耗时可以把结果压成一个数字，排队的人却不会自动变成“平均用户”。

Zipage：缓存瘦了，显存未必松一口气

KV 压缩的直觉是，把历史压小，就能省显存。但多个请求共享同一段前缀时，账没这么好算：一个请求压缩完了，其他请求还引用着原来的块；新的私有压缩结果已经分配，旧的共享块却暂时不能释放。

我沿着 Zipage 追的是首次压缩的时机：什么时候压、什么时候继续共享，才真的对容量和执行时间有利？这条线从逻辑长度一路追到了物理分配、引用关系和实际回收。

压缩率看起来很好，不代表这一刻真的腾出了同样多的显存。未来能够释放的块，也不能拿来支付眼前必须完成的分配。这些机制值得解释，但解释清楚了，还得面对强基线。

后面的对照里有固定首次压缩阈值、一个简单的共享感知规则，以及读入容量和成本信息的更复杂候选。简单规则在两组固定续写上有小幅收益，复杂候选并没有因为“知道得更多”就跑得更快。

自然生成又带来了质量取舍，换到双卡张量并行，也没有一致保留原来的性能排序。固定续写能控制要执行的内容，却不能代替新一轮生成质量评估。

这条经历很难用一句“完全失败”打发：物理账目里的问题是真实的，实验也留下了认识；但当初期待的、稳定胜过强基线的方法收益没有成立。尤其是更复杂的候选，它的信息更多，责任也更多，成绩没有跟着涨。

双平面调度：最强的方法叫“先分好卡”

还有一个想法来自让 AI 生成优化方案、再用 GPU 跑基准测试的闭环。提出方案的模型和验证方案的程序都要吃资源，我想研究它们怎么共享 GPU：动态让卡、驱逐模型、调节并发，能不能更快拿到有效反馈？

这个故事很像一个系统论文的开头。实际先测了一个简单方案：八张卡里，一张给提出方案的模型，七张给被测程序。

在那条固定任务轨迹上，静态 1+7 已经能同时工作。为了多挤出一张测试卡，把模型驱逐后再加载，反而拖慢了反馈；重新加载的成本吃掉了增加并行度的好处。同节点不同 GPU 的正式测量也没有出现我担心的方案排名翻转，明显干扰主要集中在启动阶段。

于是联合调度、测量感知调度和驱逐路线都先停下。这里需要的是能让简单分卡办法真正失效的 workload，而不是一个更长的调度器名字。

对手甚至没用上 adaptive。它只是把座位排好了。

HP TCP：最难打的对手，是睡醒了的 baseline

传输这边，我想用更快的 TCP 减少后训练中的权重同步等待。推理端要拿到训练端更新的权重，搬得快一点，听起来就能早点继续工作；手上又有正在做的传输实现，开场非常顺畅。

真正需要成立的，是它比合理调优的旧实现更好，而且省下的传输时间会暴露在最终等待里。接口接通，只完成了第一步。

受控双机对照中，某个配置下新实现看起来有优势。但调整旧实现的分块大小和并发度后，差距收窄，独立重复也没有形成稳定排序。

这时候继续扩大训练规模，很难回答眼前的问题：我改进了传输机制，还是先挑到了一个没睡醒的对手？于是“换个传输后端就能加速后训练”的这条研究支线停下，完整后训练收益也没有被验证。

工程工作继续推进。bug 要修，multi-rail 要完成，真实调用方的需求要交付；这些不需要靠一条尚未成立的论文主张来证明自己值得做。

FreshView：调度员到岗了，队伍已经散了

Agent 的记忆更新也让我想过一套方法。新经历写进来，要抽取、索引、整理；全部做完再回答可能慢，放到后台又担心下一次 query 读到旧内容。能不能知道 query 真正依赖哪些更新，先把它们处理掉？

接下来的方案几乎会自己长出来：依赖预测、动态优先级、按需物化。想法还在体检，架构图已经发育成熟。

我先看的是完美信息能省多少。在本轮测量和回放设定里，轻量记忆写入原本就便宜，固定策略往往在查询到来前已经处理完了。即使理想化依赖信息，也没有打开足够的额外收益空间。

还有一层区别：一个问题只依赖少量历史，只能说明依赖稀疏；它不能保证 query 到来时，后台恰好积压着值得重新排序的更新。数据集里的历史关系，不会自动附赠生产服务的到达时序。

所以这条线先停。更贵、更密集的更新可能改变判断，但得先找到它们。没有必要给一个还没出现的队列，安排一位很忙的调度员。

HiCache：准备发明策略，发现菜单里已经有了

我也怀疑过缓存写回：把 GPU 上的 KV 备份到主机，若后面很少复用，会不会白花搬运成本，反而让请求更慢？如果确实如此，似乎就需要更聪明地决定什么时候写、写多少。

查到同步写回路径，只能证明可能发生等待，不能证明它造成了实际净损失。于是把已有写回策略摆到一起，分别测低复用和高复用场景。

这轮重复实验中，低复用条件下预想的平均延迟损失没有稳定出现；现成的 write-back 策略又保住了高复用时的收益，同时减少了另一组负载中的写入量。

于是当前这条“还需要一个新写回策略”的命题停下。能减少写入是一个机制指标，值不值得新增方法，得看原有策略之后还剩多少实际等待。自己的方案还在起名，已有配置已经开始上班。

有几条还不能写进“被毙名单”

并发吞吐断点。 我追过增加并发后吞吐反而大幅下降的旧观测。后来跑通当前同类异构路径，并固定同一批请求比较，没有重现原来的断崖。当前结果里能看到有限任务的尾批和排空差异，但它不能解释所有历史现象。旧构建和逐步执行证据没有对齐，历史根因就仍然未定。

PD 额外首字等待。 我也想过，prefill 和 decode 分开之后，多出来的等待是否需要新的协调机制。补上普通张量并行对照后，仅改变资源划分的对照，就出现了同量级的等待；因此不能把多出来的时间全部算到 PD 协调头上。具体阶段归因还没完成，不能把不同 run 的延迟相减，就叫作 KV 传输耗时。这条暂缓，留下的是一个需要重新拆清楚的问题。

参数更新能否胜过检索。 最近还准备了一条算法实验：编程 agent 已经能检索同样的官方文档和历史经验，再用这些经验做 LoRA/SFT，能否改善未见任务，保住旧能力，并抵得上训练成本？核心对照应当是“相同检索和记忆，再额外训练”，而不是训练后的模型打一个什么都拿不到的裸模型。到写这篇时，这条线只完成了研究定位、数据划分和环境准备，随后暂停，尚未完成正式训练评测。它没有负结果，也没有正结果。

这些条目放在一起，是为了把进度写全。实验没判清和实验判输了，不该共用一个文件夹名字。

给 idea 续命，技术上总有办法

回头看，我最需要克制的反应是：收益不够，就再加点东西。固定策略打不过，就加 adaptive；分支没学好，就先扩模型；这个场景不明显，就换个更复杂的场景。

这些动作都可能合理，但每一步最好能回答一个具体问题。否则只是让原来那个没被证明的假设，住进了一个更大的工程。

现在我更愿意在动手前写下几句话：

  1. 这个问题确实发生在哪里？影响的是答案质量、用户等待，还是一个好看的中间指标？
  2. 最强的简单对照是什么？我有没有给它和自己一样认真的调优？
  3. 关键假设是什么？奖励真的错了、残差真的可学、缓存真的释放了，还是只是听起来顺？
  4. 什么证据会让我停下，什么新证据才值得重新开始？

这里面最有用的，往往是非常具体的区别：上界不是下界，存在残差不是残差可学，总耗时不是每个人的等待，逻辑压缩不是物理回收，准备完实验也不是做完实验。

它们比“科研要不断试错”难听一点，但下次真的用得上。

我还在找值得长期积累的问题，也继续做能落地的工程。至于下一个 idea——可以先不给它取四字母缩写。让它见一见调好参数的 baseline，再决定要不要印名片。
